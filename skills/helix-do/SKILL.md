# Helix Do

人决定研究意图、行动方案和下一阶段问题。Agent 恢复项目上下文，执行本轮已授权的工作，并整理事实与结论。直接使用已授权的 FlowUs 接入读取 Project 多维表、页面、原生关联和附件，先查询当前工具帮助及实际字段。

## 定位任务

- 用链接、页面 ID，或唯一匹配的 Project 和 Stage 名称确认归属。操作使用稳定 ID，标题和显示编号用于检索与呈现。目标有歧义时先处理可确定的读取，再请用户确认目标。
- 用户发 Stage 链接并显式调用 `/helix-do` 时，按下文读取上下文。若该 Stage 已明确填写「本阶段问题聚焦」和人工「行动方案」，本次调用授权按方案执行、验收并写回当前 Stage。同一轮写回「具体行动」后直接开工。用户明确要求只读、审方案或指定其他范围时，以明确指令为准。其他仅指定 Stage 的请求默认恢复上下文并给出接手摘要。
- 单独要求整理时先形成「实验结果」和「实验结论」草稿，已授权写回时直接定点更新。
- 写回实验记录的授权包含将本轮相关且有助于阅读或核验的图片、视频等附件上传到目标 Stage 并插入正文。Agent 按实验内容选择附件和位置，随报告一并写回，无需另行请求附件授权或逐件确认。用户明确限制写入范围时，以其指令为准。

## 首次读取上下文

1. **先完整读取 Project 资料。** 每个新对话首次接手 Project 时，读取项目信息、目标、背景、资料子页、嵌套块和所有项目级附件。分页续读，展开目录、引用、折叠和相关子页。项目信息承担类似 `AGENTS.md` 的工作说明，核对各 Stage 的范围、设备、工作目录、仓库、环境和验收要求。使用这些信息约束本轮获授权的操作。
2. **再读取 Stage 图结构。** 分页读完所属多维表的阶段与原生来源关联。用页面 ID 构建从来源到后续阶段的边，确认推进顺序、分支、合并和目标所处的位置。关联不完整时指出具体缺口，按实际读到的关系理解图。
3. **最后读当前 Stage 和上游正文。** 读目标的研究问题、方案、结果、证据、经验沉淀和下一阶段问题。先读全部直接父节点，再沿相关来源追溯，至少读 3 个不同的上游 Stage；不足 3 个就全部读完。根据分支和证据继续扩读，直到能说明此前做了什么、问题如何演变、当前阶段接着验证什么。查阅这些记录中影响本轮理解、执行或验收的附件和证据。展开当前及已读上游 Stage 的折叠列表，分页读完实际子块。复用「实践经验」前，核对其适用条件与本轮是否相符。

Helix Project 创建 Stage 时，会分别引用各父节点当时的「下一阶段聚焦问题」。保留这些引用与人工补充，理解其创建快照的含义。核对当前来源图与父节点正文，发现差异时指出具体来源与内容。

同一对话切换到同一 Project 的其他 Stage 时，重新定位并读取其图位置和来源链，补读有变更的项目资料。换 Project 或开新对话时，执行完整的首次读取。同一对话继续同一 Stage 时，复用已读上下文，按需核对变化。接手摘要简短交代当前阶段、问题来路、已核实进展、约束和缺口。

### 附件与缺口

- 用当前工具支持的读取方式取得实际内容。分页或分段检查长材料，区分发现文件、取得内容、实际解析范围及与实验的对应关系。文件名、大小和附件块仅用于定位。
- 附件读不到时，及时向用户报告文件、所在页面、实际错误或能力限制、受影响的判断，请用户提供可访问链接、原件、副本或必要授权。继续读取其他材料，依赖缺失证据的结论或操作等补齐后再推进。项目资料的覆盖情况按实际读到的内容报告。
- 能使用已授权的原始运行产物或副本时，核对版本、场景和归属，记录实际来源及检查范围。临时签名地址留在获取过程中，正文引用可追溯的页面、块或文件位置。

### 随读取学习文风

排除段末带 ` ✧` 的生成内容。其余旧段落可列为候选，优先选能确认由用户写的实验原因、个人总结和手写批注。来源不明的旧段落保持候选身份。只学习措辞和排版，具体看术语、段落长短、列表密度、强调方式和图注格式。可靠样本不足时沿用目标页面格式，采用简洁的技术写法。风格分析留在内部。

## 实践与栏目分工

将人工方案拆成可执行步骤，在人工方案下写回分割线和「具体行动」折叠列表，然后继续执行。把拟执行步骤和已执行事实写清楚，随实际进展更新相关内容。接手摘要和方案进度可在同一轮汇报。

Agent 开始执行已授权的实验行动时，读取当前 Stage 的原生状态属性。如果是「计划中」，将该属性改为现有选项「进行中」，并回读确认。已是「进行中」或处于其他状态时跳过。仅接手阅读、给建议或整理已有记录时不触发此更新。更新失败时报告实际状态和失败原因。

| 栏目 | 默认分工 |
| --- | --- |
| 本阶段问题聚焦 | 人工填写，保留 Project 自动带入的父节点引用。 |
| 行动方案 | 人工填写宏观解决方法。Agent 在人工方案下的「具体行动」中维护执行步骤和实操记录。 |
| 行动结果 → 实验结果 | Agent 在标题下用可见正文记录关键操作、条件、观测和证据。补充细节可在相关正文后按需折叠。 |
| 行动结果 → 实验结论 | Agent 在标题下用可见正文回答本阶段问题，交代证据支持的判断、成立条件和待验证项。 |
| 行动结果 → 经验沉淀 | 保留人工记录。Agent 将本轮值得复用的经验写入「实践经验」折叠列表，供后续任务接手时参考。 |
| 下一阶段聚焦问题 | 人工填写。 |

用户主动询问时，可就问题聚焦、行动方案和下一阶段问题给出建议，建议先留在对话中。计划或意图有缺口时，先完成可确定的读取和整理；涉及研究取舍或执行条件的缺失信息再请用户明确。按实际执行记录条件与产物，保留多轮尝试的身份及先后关系。

接手摘要、建议、草稿和正式记录均采用 [实验记录与验收](references/recording.md) 中的排版规则。整理或写回记录前，阅读其中的内容组织、反防御性写作和验收要求。先核对当前问题、上游基线与实际证据，再写清正文，按需附上折叠细节。只按授权维护目标 Stage 的相应内容。其余状态变更、完成日期、来源和模板按各自的明确任务维护。

## 长任务与收尾

- 默认在当前对话持续跟进到验收和写回。记录可重新定位的作业 ID、运行环境、日志及产物位置。复用现有日志和指标。
- 按下一次可获得有效证据的时间与可接受的故障发现延迟确定检查点。启动或续跑后，优先检查首个能确认作业正常推进的信号。稳定后，可等到下一次评估、检查点或预计结束，但检查时间不得晚于可接受的故障发现时限。结合重跑成本、资源占用和任务紧迫性判断这个时限。进度停滞、指标异常或预计完成时间明显变化时，重新确定下一次检查时间。
- 确定检查点后，优先用一次可中断的原生 `sleep` 等到该时间点，秒级时长换算为整数毫秒。单次 `sleep` 上限为 12 小时（43,200,000 毫秒），并遵守当前工具实际支持的时长。超过单次上限时，按原定检查时间计算剩余时长并续等，只在到达检查点后查询作业。到点先取作业状态、进度和关键指标，异常时再定位相关日志。
- 正常结束后直接核对退出状态、产物、指标和项目验收条件，写回并回读「实验结果」「实验结论」、相关附件及本轮有复用价值的「实践经验」。按证据记录低于预期的结果。发现异常时，先诊断并在原方案范围内修复、续跑，重试前确认原作业状态，避免重复启动。
- 关键事实缺失或相互矛盾、缺少权限、或恢复需要改变实验条件时，停下依赖该决定的操作。说明具体问题、已核实的状态、作业 ID 和恢复点，等用户明确答复。恢复时先核对当前作业与记录，再继续。
- 用户明确要求跨轮续跑时，可用环境支持的 Goal，完成条件包含验收、写回和回读。按当前 Goal 工具的状态规则处理实际阻塞和恢复。
